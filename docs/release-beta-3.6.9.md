# «Монтажная» beta 3.6.9 — потоковый MP4 через FFmpeg image2pipe

## Цель обновления

В beta 3.6.8 финальные кадры композиции передавались из Renderer в главный процесс Electron, сохранялись как нумерованные PNG в каталоге временной сессии, а после завершения FFmpeg перечитывал эту последовательность для кодирования MP4. На высоком разрешении и сложных изображениях это приводило к быстрому исчерпанию дискового лимита 2 ГиБ.

В beta 3.6.9 выходные кадры передаются в уже запущенный FFmpeg через бинарный stdin в формате `image2pipe`. Нумерованная последовательность финальной композиции больше не сохраняется на диск.

## Новый путь экспорта

1. Renderer начинает экспорт с `streamFrames: true`.
2. Главный процесс создаёт сессию и выполняет предварительную проверку дискового пространства без оценки постоянной выходной PNG-последовательности.
3. Исходные видео по-прежнему декодируются FFmpeg в отдельный дисковый кэш точных кадров для композиции таймлайна.
4. Подготовленный WAV (если есть звук) передаётся из Renderer во временное хранилище порциями через существующий staged-file API. Размер и сигнатура WAV проверяются, ffprobe сверяет длительность с планом.
5. Главный процесс запускает локальный FFmpeg с входом `-f image2pipe -vcodec png -framerate FPS -i pipe:0`; WAV подключается вторым входом.
6. Renderer композиционно отрисовывает один кадр, получает PNG через `canvas.toBlob()`, передаёт бинарные данные через узкий IPC API и ждёт подтверждения записи перед переходом к следующему кадру. Такая последовательность создаёт backpressure и ограничивает количество одновременно передаваемых кадров.
7. FFmpeg кодирует H.264 с постоянной частотой кадров, при наличии звука добавляет AAC 48 кГц, передаёт прогресс через `-progress pipe:1`.
8. После последнего кадра stdin закрывается. Главный процесс дожидается реального `close`, проверяет MP4 через ffprobe, декодирует файл в null для проверки ошибок, проверяет доступное место и только затем копирует MP4 в целевой каталог.

## Отмена и очистка

Текстовая команда `q` не может отправляться в бинарный PNG-поток. При отмене потоковый процесс завершается сигналом процесса, а после grace-period применяется принудительное завершение. Сессия и временные данные удаляются только после фактического закрытия FFmpeg. При ошибке Renderer прекращает передачу кадров и вызывает отмену сессии.

## Дисковое пространство

В режиме `streamFrames` потребность в постоянной последовательности выходных PNG равна нулю. В preflight и runtime-расчёте по-прежнему учитываются:

- отдельный дисковый кэш PNG-кадров, извлечённых из исходного видео для точной композиции;
- временный WAV;
- временный MP4;
- копия конечного MP4 и резерв свободного места.

**Ограничения, которые не сняты этим обновлением:** кэш исходных декодированных кадров ограничен 2 ГиБ на сессию; WAV — 512 МиБ; декодированный OfflineAudioContext/AudioBuffer ограничен существующим лимитом Chromium в приложении. Потоковый MP4 не означает потоковое декодирование/хранение всех исходных кадров. Эти задачи остаются в бэклоге.

## Ограничение ресурсов FFmpeg

Для входной очереди image2pipe задаётся ограниченный `thread_queue_size`, а libx264 запускается с ограниченным числом потоков. Это уменьшает риск избыточного расхода RAM и не позволяет FFmpeg свободно накапливать много больших PNG-пакетов. Это осознанный компромисс: скорость кодирования на мощных компьютерах может быть ниже, чем при автоматическом выборе всех потоков.

## Изменённые компоненты

- `electron/frame-sequence.cjs` — построение параметров FFmpeg image2pipe.
- `electron/managed-process.cjs` — последовательная бинарная запись с ожиданием callback/backpressure и отмена без текстовой команды в PNG-потоке.
- `electron/main.cjs` — запуск FFmpeg до передачи кадров, runtime-сессия, прогресс, проверка/копирование результата, очистка.
- `electron/preload.cjs` — узкие IPC-методы запуска потока и передачи WAV через staged-file API.
- `electron/disk-space.cjs` — исключение постоянных выходных PNG из оценок в потоковом режиме, сохранение расчётов исходного кэша, WAV и MP4.
- `src/renderer/index.html` — потоковый цикл MP4, обновлённая справка и версия 3.6.9.
- `tests/streaming-ffmpeg-integration.test.cjs` — интеграционные тесты реального FFmpeg, включая 4K.

## Известные ограничения

- Исходный кэш PNG для видео остаётся дисковым и ограничен 2 ГиБ.
- WAV/OfflineAudioContext пока не полностью потоковые.
- `canvas.toBlob()` и IPC временно удерживают один текущий PNG-кадр; размер отдельного кадра ограничен валидацией модуля.
- Проверка выполнена в Node/FFmpeg тестовом окружении. Полный GUI/Electron запуск, длительный 4K-проект и Windows PowerShell installer требуется проверить на пользовательской системе.
- Тест 4K в CI проверяет 3 кадра 3840×2160, это smoke/integration test, а не доказательство длительного 4K60 экспорта.

## Совместимость

Формат проекта и структура таймлайна не меняются. Изменяется только способ отправки финальных кадров в локальный MP4-кодировщик. WebM и встроенный realtime MP4 не переходят на этот путь и остаются отдельными режимами.
