# Отчёт по проверке экспорта — 17 октября 2026 года

## Объём изменений

- Полная проверка PTS выходного MP4 вместо проверки только первых 300 кадров.
- Проверка отсутствующих, повторяющихся и непоследовательных временных меток, отклонений межкадрового интервала и крупных разрывов.
- Приёмка в интерфейсе сверяет результат с плановым числом кадров и требует подтверждения проверки всех PTS.
- Добавлены Node.js-тесты, проверяющий скрипт готового MP4 и синтетические тестовые медиафайлы с тремя звуковыми маркерами.

## Не выполнено / остаётся открытым

- Не удалось запустить исходное Windows-приложение Electron в текущей Linux-среде: поставленная зависимость Electron содержит Windows-бинарник. Попытка запустить доступный Chromium в headless-режиме в этой среде также не позволила провести интеграционный захват.
- Следовательно, реальный Canvas → `captureStream()`/`MediaRecorder` через окно приложения не был проверен в этой среде. Три результата FFmpeg — это тесты анализатора и моделируемого конвейера, а не доказательство, что браузерный захват больше не теряет кадры.
- Для завершения приёмки нужно на Windows выполнить `npm.cmd test`, запустить приложение через `npm.cmd start`, экспортировать эталонные ролики через интерфейс и проверить готовые MP4 командами из `export-validation.md`.

## Дополнительное исправление гонки перемотки — 17 октября 2026 года

После проверки на Windows проявился отдельный сбой: свойство `currentTime` обновлялось до завершения асинхронного seek/decode, а код трактовал это как завершённую перемотку. Исправлены `waitForSeekedTo()` и допуск временных меток в `src/renderer/index.html`. Добавлен регрессионный тест, в котором `currentTime` обновляется сразу, а `seeked` приходит позже; тест подтверждает, что функция не завершает ожидание раньше события.

Дополнительно `requestVideoFrameCallback` получает короткое окно после настоящего `seeked`; если Chromium не подтверждает compositor callback для паузного кадра, резервный путь допускается только при `readyState` с доступными видеоданными, `seeking=false` и текущем времени в узком допуске менее четверти кадра (не более 10 мс). Это направлено на устранение зависания и принятия старого кадра до реальной перемотки.

После изменения: `npm test` — 7/7 PASS; `node --check` для main/preload и встроенного JS renderer — PASS. Реальный экспорт этой версии в Electron на Windows пока не выполнен; поэтому исправление остаётся кандидатом до прямого сравнения нового MP4 с оригиналом по содержимому кадров.


## Дополнение v9 — 2026-10-17

Убран запуск кратковременного воспроизведения только ради `requestVideoFrameCallback`: на реальном Electron оно сообщало следующую временную метку (например, 0.167 с) при целевом seek 0.125 с. Теперь подтверждение основывается на завершённом `seeked`, доступности декодированного изображения и повторной проверке `currentTime`. Это исправляет ложный отказ от экспорта; реальный выходной файл всё ещё нужно проверить сравнением с оригиналом.
