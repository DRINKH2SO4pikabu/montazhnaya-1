# Изменение экспортного конвейера — v13

## Почему изменён подход

В предыдущих версиях MP4 временная шкала и контейнер могли содержать правильные 240 кадров / 24 FPS, но изображения повторялись/пропускались. Проверки PTS подтверждали только временную сетку, а не содержание каждого кадра.

Документация MDN и web.dev подчёркивает, что `HTMLMediaElement.currentTime` задаёт позицию по времени, а не номер декодированного кадра; `seeked` сообщает о завершении операции перемотки, но сам по себе не задаёт точный номер исходного кадра. `requestVideoFrameCallback()` полезен для наблюдения за кадрами, представленными композитору, но не превращает обычный `<video>` в frame-accurate декодер. Поэтому последовательность патчей, пытавшихся подтвердить кадр через `currentTime`/`seeked`/`requestVideoFrameCallback`, устраняла отдельные гонки, но не давала гарантии точного отбора исходного изображения.

## Новый путь MP4

Для локального MP4 кадры источника теперь декодируются локальным FFmpeg на сетке выходной частоты:

1. Рендерер вычисляет множество исходных индексов, реально нужных клипам на каждом временном шаге экспорта. Индекс определяется после нормализации времени клипа: `round(sourceTime * outputFps)` с ограничением последним допустимым кадром источника.
2. Рендерер передаёт исходные байты видео в главный процесс Electron через узкий preload IPC. Сейчас размер одного исходника ограничен 128 МиБ.
3. Главный процесс записывает исходник во временную папку, подтверждает видеопоток через `ffprobe`, а FFmpeg выполняет `setpts=PTS-STARTPTS,fps=...:round=near` и затем `select` только требуемых индексов. Вывод ведётся в PNG, без real-time MediaRecorder и без browser seeking. Длинные списки индексов разбиваются на небольшие фильтры, чтобы не упереться в предел длины командной строки Windows.
4. Для каждого кадра таймлайна рендерер получает нужные PNG, использует их в существующем Canvas-композиторе (`drawClipFrame`, масштабирование, поворот, цветовые настройки, переходы и надписи) и сохраняет результат композиции отдельным PNG.
5. FFmpeg собирает нумерованные композиционные PNG в H.264 MP4 с заданными FPS и количеством кадров; оффлайн-сведённый WAV по-прежнему мультиплексируется отдельно. Финальный MP4 проходит проверку контейнера, временных меток и декодирования.

## Почему source PNG и композиционные PNG разделены

Исходный декодер должен выбирать правильный кадр источника; композиционный слой отвечает за свойства клипа и переходы редактора. Разделение позволяет сохранить существующую логику композитора, не поручая Chromium точную перемотку. Исходные PNG кэшируются на диске в пределах сессии экспорта; в памяти рендерера одновременно удерживается ограниченный кэш декодированных картинок.

## Валидация и ограничения

- IPC принимает только запросы от доверенного основного окна и проверяет session id, медиа id, возрастающие индексы, сигнатуры PNG, размеры файлов и общий лимит временных PNG.
- Если FFmpeg не выдаёт ровно столько PNG, сколько было запрошено, экспорт должен завершиться ошибкой, а не продолжаться с молчаливыми пропусками.
- Один исходный видеофайл ограничен 128 МиБ для текущей реализации IPC. Общий объём временных PNG ограничен 2 ГиБ. При превышении экспорт должен явно завершиться ошибкой.
- `fps`-фильтр формирует CFR-представление источника для требуемой частоты выхода. При преобразовании, например, 24 → 30 FPS некоторые исходные картинки закономерно повторяются, потому что выходная сетка плотнее. Это не потеря кадров захвата; при 24 → 24 FPS на тестовом 24 FPS источнике должны сохраняться все исходные изображения.
- `npm test` проверяет логику построения FFmpeg-команды и на синтетическом ролике подтверждает, что выборочные PNG совпадают с кадрами тех же индексов в полном CFR-декодировании. Этот тест не запускает Electron UI и не доказывает end-to-end экспорт всех эффектов на Windows.

## Проверка на предоставленном оригинале во время разработки

Для файла `video (3)(7).mp4` (1280×720, 24 FPS, длительность контейнера около 10.005 с) была выполнена независимая проверка выборочного декодирования: FFmpeg создал полную CFR-последовательность из 240 PNG, затем новый source-frame extractor создал выборку всех 240 индексов. SHA-256 каждого выбранного PNG совпал с PNG того же индекса в полном декодировании: **240/240 совпадений**. Это подтверждает корректность FFmpeg-команды выбора источника на данном файле. Это **не** заменяет запуск полного экспорта через UI Electron в Windows; композиция, IPC и аудио ещё должны быть проверены в пользовательской сборке.

## Команды проверки

Из корня проекта:

```powershell
npm.cmd test
npm.cmd start
```

После установки нужно экспортировать исходное `video (3).mp4` на 10 секунд с 24 FPS в последовательности и MP4. Проверять следует не только `ffprobe` (240 кадров, 24 FPS, 10 секунд), но и изображения: в простом тесте 1 видеоклип без эффектов/переходов сравнить последовательность кадров с оригиналом. При ожидаемом совпадении FPS повторы вида `0,0,1,3,3,4...` недопустимы. Затем отдельно проверить звук по маркерам.
