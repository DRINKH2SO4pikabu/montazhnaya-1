# «Монтажная» beta 3.6.10 — оконный LRU-кэш исходных кадров

## Цель

Заменить прежнее накопление всех декодированных PNG-кадров исходных видео в экспортной сессии на ленивое декодирование ограниченными окнами. Это устраняет прежний общий предел 2 ГиБ для исходного frame cache в потоковом MP4-пути, не превращая кэш в неограниченное хранилище.

## Что изменено

- Main process регистрирует исходный медиаресурс, `start_time`, размеры, FPS и список нужных CFR-индексов. На этапе регистрации всё видео больше не декодируется заранее.
- При запросе Renderer Main process выбирает небольшое окно вокруг требуемого source-frame index и декодирует только отсутствующие кадры.
- Для последующих окон используется `-copyts` и входной `-ss`, рассчитанный относительно начала видеопотока. Фильтр сбрасывает timestamps относительно абсолютного времени начала окна (`stream start_time + frameIndex/FPS`) и применяет прежнюю CFR-сетку. Это сохраняет фазу кадров при 24/25/30/60 FPS.
- Размер окна начинается с 48 запланированных индексов и динамически уменьшается, если консервативная оценка raw RGBA или фактический размер PNG превышает бюджет. Окно также ограничено временным span, чтобы sparse-список клипов не заставлял декодировать огромные промежутки.
- Дисковый LRU-кэш исходных PNG — максимум 512 МиБ на сессию. При заполнении удаляются наименее недавно использованные кадры. Если вытесненный кадр понадобится повторно, он будет декодирован снова.
- Renderer учитывает декодированные поверхности как `width × height × 4`, поддерживая бюджет 256 МиБ. Единичный кадр, превышающий весь бюджет, не сохраняется в постоянном Renderer-кэше.
- Предварительная оценка свободного места для нового окна использует до raw RGBA bytes + overhead, а не оптимистичные 30% сжатия PNG.
- Staged-исходники из портативных/памятных файлов сохраняются до закрытия экспортной сессии и очищаются на успехе, ошибке или отмене.

## Ограничения и компромиссы

- 512 МиБ — ограничение одновременно хранимого дискового кэша, а не длительности исходного видео. При нелинейном повторном доступе вытесненные кадры могут декодироваться повторно.
- Renderer cache ограничен 256 МиБ, но текущая композиция всё равно должна удерживать изображения всех одновременно активных слоёв до завершения отрисовки текущего кадра.
- Максимальный размер отдельного PNG исходного кадра остаётся 64 МиБ.
- Ограничения WAV (512 МиБ) и OfflineAudioContext/AudioBuffer (256 МиБ) этим этапом не снимаются.
- Лимит 2 ГиБ для legacy-операций записи нестримовой PNG-последовательности остаётся; streaming MP4 не сохраняет всю итоговую PNG-последовательность на диске.
- Для исходников с необычными временными шкалами, VFR, нестандартными edit lists и многослойными монтажами требуется ручной regression test в Windows/Electron.

## Проверки

- Побитовое сравнение PNG, извлечённых полным CFR-декодированием и ленивыми окнами, для 24/25/30/60 FPS.
- Отдельный тест с ненулевым `videoStream.start_time` (0,5 секунды).
- Проверка окон у начала, в середине и у конца исходного ролика, включая последние кадры.
- Проверки LRU eviction, byte budget, sparse frame plans и консервативной оценки дискового пространства.
- Полный автоматический набор: **113/113 тестов**, 0 ошибок, 0 пропусков.
- Реальные FFmpeg 7.1.5 integration tests запускаются в рабочем окружении. Windows GUI/Electron и длинный многослойный 4K экспорт на пользовательском компьютере ещё требуют ручной приёмки.

## Файлы

- `electron/source-frame-cache.cjs` — выбор окна, оценка байтов, LRU-план вытеснения.
- `electron/frame-sequence.cjs` — FFmpeg args с точным seek и сохранением CFR phase.
- `electron/main.cjs` — ленивое декодирование, disk LRU и очистка staging.
- `electron/disk-space.cjs` — консервативная оценка предстоящего source window.
- `src/renderer/index.html` — byte-bounded cache декодированных изображений и сведения о новой схеме.
- `tests/source-frame-cache.test.cjs`, `tests/source-frame-extraction.test.cjs`, `tests/disk-space.test.cjs`, `tests/slideshow-builder.test.cjs` — проверки кэша, CFR, ресурсов и версии.
